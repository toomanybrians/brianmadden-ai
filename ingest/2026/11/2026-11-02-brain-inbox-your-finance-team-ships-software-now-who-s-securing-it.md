# ⚙️ Your finance team ships software now. Who's securing it?

## Insights

- As AI tools let non-developers (marketers, finance, ops staff) build their own software and automations, the security/access decisions that used to belong to professional developers now fall to whoever opens an AI tool — often without the expertise to make them.
- AI doesn't map onto the traditional governed layers of enterprise IT (applications, data, compute); it touches all three but is owned by none, so it tends to run ungoverned in the gaps between them.
- Three common failure modes are identified, none resembling a traditional security attack: oversharing data into tools that retain/train on it, agents being granted (and using) more access than a task requires, and nobody being accountable because no one made an explicit usage decision.
- Approved-tool lists are argued to be an insufficient governance mechanism, since they constrain tool choice but not what a connected agent can actually reach — and employees route around tools that can't do the job.
- The alternative framed here is governing the runtime environment itself via five combined controls: contain the data, scope the access, govern the models used, audit activity, and control spend — argued to only work as a package (e.g., scoped access without containment can still leak).
- The piece suggests this is an extension of existing platform-team responsibilities (environment/access setup for developers) rather than a new function, now widened to cover business users building with AI.

## Quote

> Control that depends on good behavior, human or model, isn't control.
